# TEST_PLAN — Stretch

Principles: engine first; tests never need Ollama (use `StubModelAdapter`); the eval harness is the only place that needs a live model; no real data anywhere.

## 1. Engine tests (P0, gate G1)

1. **Golden**: load `fixtures/engine_golden.json`; assert `runway`, `safe_spend`, `reserve`, `affordability`, date resolution, essentials conversion, and validation-error cases equal the expected values. Hand-checkable examples: `G01` (9000 at 1000/day -> 9 days, runs out Oct 14), `G02` (inflow on day 0 counts), `G03` (same-day inflow and commitment), `G09` (15001 x 0.5 floors to 7500).
2. **Property tests** (hypothesis, bounded ranges): delaying an inflow never increases `runway_days`; reducing an inflow (factor <= 1 or smaller `new_amount`) never increases it; cancelling never increases it; adding an expense never increases it; `runway_days <= horizon_days`; series length equals `horizon_days`; engine result is identical on repeat calls (determinism).
3. **Validation**: `invalid_date`, `conflicting_adjustment`, `unknown_inflow`, `out_of_bounds` raised exactly per `engine_golden.json -> validation_error_cases`.
4. **Purity**: an AST test asserts `stretch/engine/*.py` import only `datetime, math, dataclasses, typing, enum, functools, __future__`.
5. If a golden case fails, **derive by hand** (day-by-day) before touching a fixture, and report both numbers to the human.

## 2. Tools and verification tests (P0)

- **Registry**: each tool executes the arg models with bounds; the demo plan in `fixtures/ask_demo_plan.json` produces a `ToolResult` equal to `fixtures/ask_demo_execute.json` (ignoring key order).
- **V1**: amounts must be found in the text after normalization (`26k`, `1,500`, `₦14,200`, `1.5k`); a made-up amount is flagged `grounded:false`.
- **V2**: rejects unknown tools, out-of-bounds values, unknown `inflow_id`, both `amount_factor` and `new_amount`, both `delay_days` and `new_date_expr`; one repair attempt via the stub; clarify/refuse plans pass through.
- **V3**: `ask_demo_narrate.json` passes; `v3_failure_example.json` fails with unmatched `["22","17"]`; denylist words (loan, invest, crypto, borrow) fail; template narration for every preset passes.

## 3. API and mode tests (P0)

- Contract tests for every endpoint in `API_CONTRACT.md` using fixtures; error shapes and codes.
- **Modes**: `STRETCH_PERSIST=0` writes no files; `STRETCH_HANDOVER=1` forces user profile, in-memory store, metadata-only traces (read the trace file: it must contain no amounts, no question text, no arguments); `/api/situation/demo` returns 403 outside the demo profile.
- **Fallback E2E (P0-11)**: `STRETCH_LLM=off` and a dead Ollama URL: manual setup -> confirm -> `/runway/scenarios` -> `/ask/direct` (afford form) all succeed and equal the golden values; `/ask/plan` returns 503 `llm_unavailable` with `fallback:"manual"`.
- **Socket block (PR-2)**: a pytest fixture patches `socket.socket.connect` to allow only loopback addresses; run the full pipeline (stubbed model) and assert no violation.
- **Fixture hygiene (PR-5)**: every fixture with a situation has `"synthetic": true`.
- **Few-shot disjointness**: no few-shot example text used in prompts equals or contains any `eval/cases.jsonl` text.

## 4. Frontend checks (P0, manual + light automation)

- Renders from fixtures with no backend (mock layer).
- Confirmation card highlights ungrounded/missing fields; edits propagate to the PUT payload.
- Banners: LLM down, session mode, sample data.
- No localStorage/IndexedDB usage (grep).
- `npm run build` succeeds.

## 5. Live model checks (P0 item 7)

L0 smoke on a real local model: `E01`, `Q01`, `Q02`, `X02`. Pass = valid structured output, V1/V2 pass, correct plan per scoring rules in s7. Record raw outputs even on failure.

## 6. Evaluation harness (P1)

**Command:** `python -m eval.run --models <ids|all> --cases <all|ids|N> --level L0|L1|L2|L3 --out eval/results/<run-id>`. It calls the **same production functions** (`extract`, `plan`, `execute`, `narrate`), temperature 0, pinned model tags and digests, versioned prompt files, and writes:
- `results.json`: per case x model x stage: raw output, parsed output, verdicts, token counts, ttft, total latency, failure tags.
- `results.md`: generated summary tables.
- `raw/`: raw model text for failures.
- `docs/DECISION.md`: generated by `python -m eval.decide` applying the pre-registered rule (s8). Hand-edits to numbers are forbidden.

**Cases:** 25 synthetic cases in `eval/cases.jsonl` (8 extract, 14 question, 3 adversarial). Situations: `demo_main`, `demo_two_inflows`. The planner receives only compact context: `as_of`, inflow ids+labels, commitment ids+labels.

**Metrics**

| Metric | Definition |
|---|---|
| **Tool-call correctness** | case level: normalized plan equals gold or an `also_accept` alternative; field level: tool name, and each arg |
| **Scenario interpretation accuracy** | after canonicalization, the resulting `ScenarioSpec`(s) equal gold (labels ignored, defaults filled, `scenario:null` == empty adjustments, `"*"` is not auto-expanded except where `also_accept` allows) |
| **Extraction accuracy** | field level: `balance`, essentials `{amount, period}`, inflows and commitments matched by (amount, date_expr) irrespective of order, `has_uncertainty_note` boolean, `missing` set equality; **ungrounded amounts accepted** counted separately (must be 0) |
| **Adversarial** | `clarify`/`refuse` expected; a guessed plan counts as a failure; an invented `inflow_id` counts as a failure |
| **Numerical consistency** | (a) engine vs golden: pure test, no model. (b) for the 14 question cases, run the gold plan through the engine and have each model narrate (P1 composer only): raw V3 pass rate, regenerated rate, template-fallback rate |
| **Latency** | ttft and total per stage; p50 and p95; cold-load time; tokens/s |
| **CPU / resources** | psutil sampling at 0.5 s of the Ollama server process and its children (on Windows, locate by process name `ollama*` and children; **VERIFY** and fall back to system-wide CPU % and RSS delta if detection fails): peak RSS, mean and peak CPU % |
| **Failure cases** | tagged: `invalid_json`, `schema_violation`, `wrong_tool`, `wrong_arg`, `ungrounded_number`, `scope_failure`, `timeout`, `invented_id` |

**Run hygiene.** Close the IDE, browser tabs and other heavy apps for the L3 latency run; record machine state (power plan, battery vs mains, background load). Never edit latency numbers out of results. Report the conditions in the article.

## 7. Normalization rules for scoring

- Ignore `label` fields everywhere.
- Fill defaults before comparing (`null`, `false`).
- Amounts are compared as integers; `amount_factor` as float with tolerance 1e-9.
- `date_expr` compared structurally; `{"kind":"iso"}` is accepted if it equals the resolved gold date.
- Plan equivalence classes for the demo question: `compare_scenarios([on-time, late5-half])` or `compute_runway(late5-half)` (see `ask_demo_plan.json -> also_accept`).

## 8. Pre-registered decision rule (fixed before any results)

- **Qualify** a model if: S1 + S2 combined >= 20 of 25 cases, **zero ungrounded amounts accepted**, and zero invented ids on `X03`. S3 (composer): raw V3 pass rate >= 70% on the 14 question cases, otherwise that model gets template-only narration.
- **Select** the highest-scoring qualifying model (ties: lower p50 latency). A single model for all stages is preferred unless another beats it by >= 10 points on a stage.
- If **no model qualifies**: the manual form becomes the primary setup, the LLM planner is labelled experimental, and the README says so.
- **Gemma claim:** only per `ACCEPTANCE_CRITERIA.md` s6.
- A reduced L2 (>= 12 cases, chosen and recorded before running) uses the same thresholds scaled proportionally (>= 80% of cases) and is labelled "reduced" in `DECISION.md`.

## 9. Manual demo rehearsal (before recording and before handover)

1. Fresh start: `STRETCH_PROFILE=demo`, load sample data; confirm dashboard numbers equal `runway_presets_demo.json`.
2. Paste the demo paragraph; confirmation card shows all values grounded.
3. Ask the demo question; ribbon steps run on real responses; numbers equal `ask_demo_execute.json`.
4. Ask `Should I take a loan or put the money in crypto?` -> fixed refusal. Ask `What if it comes a bit late?` -> clarifying question.
5. Stop Ollama; reload: banner appears, manual path and presets work.
6. Handover mode: `STRETCH_HANDOVER=1`; confirm nothing is written to `data/` (list the folder before and after).
7. Record the demo only on synthetic data.
